# 아이샵케어 Full Stack Developer (Node.js) 사전 과제

구매 상담 정보를 받아서 저장하고, 내부 Admin에서 검색/필터 조회하는 기능을 제공하는 API 서버 어플리케이션을 구현해주세요.

## 📌 제약 사항

- 🟦 **TypeScript**로 구현해 주세요.
- 🧱 기존 `ishopcare-preview-test` 레포의 코드 베이스를 활용하되, 자유롭게 수정하셔도 괜찮습니다. 단, **NestJS 아키텍처**는 가능하면 적극 활용해 주세요.
- 🤔 위 조건 외에는 **개인 판단**에 따라 효율적인 방식으로 구현해 주세요. **모든 지원자 분들께 동일한 경험을 제공해 드리기 위해, 개별적인 과제 관련 문의 사항은 답변 드리기 어려움을 양해 부탁 드립니다.**

## ⚙️ 과제 템플릿 초기 세팅 방법

- 📦 `pnpm install` 를 통해 의존성 패키지를 설치합니다.
- 🔧 본 과제 템플릿은 **Node.js 20** 버전에서 작성되었습니다. `Node 20` 이상 버전을 사용하길 권장드립니다.
- 🧬 `pnpm schema:generate` 실행 시 `sqlite3` 파일이 생성됩니다. `inquiry-entity.ts` 코드를 수정한 경우, 해당 명령어로 스키마를 업데이트해주세요.
- 🚀 `pnpm start:dev` 를 통해 서버 및 배치 작업을 실행시킵니다. http://localhost:8081/api-docs에 접속하면 swagger 문서를 확인할 수 있습니다.

## 구현의도

1. 암호화 AES-256-CBC와 SHA-256을 사용한 이유
   개인정보의 안전한 저장과 효율적인 검색을 위해 AES-256-CBC와 HMAC-SHA256을 혼합한 보안 아키텍처를 설계했습니다.
   - AES-256-CBC, 가변 암호화 : 복호화가 필요한 민감 정보는 AES-256-CBC 방식을 적용했습니다. 동일한 평문도 암호화되면 결과값이 달라지기때문에 데이터베이스가 탈취되더라도 관계적 추론이나 패턴 분석을 통한 데이터 복원이 차단됩니다.
   - HMAC-SHA256, Blind Index를 활용한 검색 최적화: 암호화된 상태에서 검색을 지원하기 위해 별도의 Blind Index 컬럼을 운영합니다. Salt와 Global Pepper가 결합된 단방향 해시값을 인덱싱하여, 암호 키를 모르는 공격자가 오리지널 데이터를 유추하는 것을 방지하며 DB 인덱스를 통해 빠른 조회가 가능하도록 구현하였습니다.
   - 키 분리 및 보안 강화: 암호화에 사용하는 키와 검색용 인덱스 생성 키를 물리적으로 분리하여 관리합니다.

2. 데이터 유효성 검증
   데이터의 정합성을 확보하고 향후 확장성을 고려하여 입력 단계부터 엄격한 검증 로직을 적용하였습니다.
   - NestJS의 @IsPhoneNumber 데코레이터를 활용하여 한국(KR) 국가 번호, 지역 번호, 서비스 번호(070, 080 등)의 복잡한 규칙을 정밀하게 검증합니다. 이를 통해 하이픈 유무나 공백 등에 상관없이 유효한 번호만을 수집합니다.
   - 하이픈 제거를 통한 데이터 단일화: 저장 시 모든 전화번호에서 하이픈과 같은 불필요한 서식을 제거하고 숫자 데이터만 추출해 저장합니다. 이는 저장 공간의 효율성을 높여주며 향후 UI/UX 요구사항 변경에 따라 다양한 포맷으로 가공하여 출력하기 용이한 구조를 만들기 위함입니다.
   - 추가구현 : 추후 onfigModule 설정 시 validationSchema(Joi 등)를 사용하여 서버 실행 단계에서 환경 변수를 강제하면 가독성과 유효성 검사가 더 용이한 설계가 될것 같습니다.

3. 대용량 데이터 처리를 위한 배치 시스템 구현
   수십만 건 이상의 데이터를 안정적으로 처리하기 위해 리소스 관리와 연속성을 보장하는 배치 서비스를 설계하였습니다.
   청크(Chunk) 단위 처리를 통한 메모리 최적화: 대량의 데이터를 한 번에 로드하지 않고 100건 단위의 청크로 분할 처리하여 메모리 누수를 방지하고 시스템 안정성을 확보하였습니다.
   장애 복구 및 이어하기 기능 : last_checked_at 메타데이터를 활용하여 배치 작업이 중단되더라도 마지막으로 처리된 시점부터 재개할 수 있는 메커니즘을 구현하였습니다.
   실행 시간 제한 및 중복 방지 : 서비스 부하가 적은 자정부터 새벽 3시까지 작업 시간을 제한하고 isRunning 플래그를 통해 작업의 중복 실행을 방지하는 안전장치를. 마련하였습니다.

4. 품질 보증 및 확장성 고려
   - 테스트 자동화를 통한 안정성 검증 : 유닛 테스트 코드를 작성하여 비즈니스 로직의 요구사항 이행 여부를 확인하고, 코드 변경 시 발생할 수 있는 사이드 이펙트를 사전에 차단하고자 노력했습니다.
   - 추가구현 : 현재의 낮은 테스트 통과율을 보완해 통과율을 향상시켜 보다 안정성있는 로직 검토를 진행해야합니다.
